工具调用已经超时返回，后台却又出现了它的请求记录。排查这种问题时，很容易先怀疑上游没有处理取消。但取消也可能在当前进程里就断了：调用方放弃了结果，负责生产这个结果的任务却没有收到通知。

一个足够小的例子就能暴露这个缺口。执行器只有一个并发名额，任务 A 正在阻塞等待；任务 B 已经过调度器，进入执行器队列。此时取消 B 的调用方，等待取消处理到达受测边界的同步点，再解除 A 的阻塞。如果 B 随后开始工作，说明取消没有阻止这项排队工作。不能一发出 `cancel()` 就立即放行 A，否则 B 可能抢在取消被处理前启动。

## 结果通道与执行任务并不总是同一条链

下面是一种常见的组织方式：调度器创建一个 `Future` 交给调用方等待，另外创建一个 task 执行工作，完成后把结果填回这个 `Future`。

```text
调用方 ── await result_future
                   ↑ 写入结果
调度器 ── execution_task ── 执行器队列 ── 工作线程
```

调用方取消时，正在等待的 `Future` 可以进入取消状态，但这不会自动告诉另一条执行链应该结束。[Python 的任务文档](https://docs.python.org/3/library/asyncio-task.html#task-cancellation)说明，取消通过在任务中抛出 `CancelledError` 实现；应用层还需要把这个请求传到真正执行工作的 task。

只从调度器队列中删除 B 也可能太晚。B 一旦被派发，就已经不在那个队列里了，接下来等的是执行器的名额。排查时必须确认任务现在位于哪一层，不能只检查最外层队列是否为空。

## 给每个任务保留执行句柄

调度层需要保存每个 job 对应的执行 task，并在调用方取消时找到它。下面只展示已经派发后的取消传播片段；`job.result` 是结果通道，`job.execution` 是这个 job 自己的执行句柄。

```python
import asyncio

async def wait_for_result(job):
    try:
        return await job.result
    except asyncio.CancelledError:
        if job.execution is not None:
            job.execution.cancel()
        raise
```

接收方也必须配合：还没开始的工作应被移除，或在开始前检查取消标记；清理完成后继续传播取消。迟到的结果不能把一个已取消的请求重新写成成功。

这里的粒度是单个 job。调度器可能有共用的探测协程或管理任务，取消其中一个请求时，不应顺手取消这些共享对象，否则其他排队请求也会失去进展。

## 并发名额跟着真实工作释放

工作已经进入阻塞线程后，情况又不同了。调用方停止等待，并不意味着 Python 能强制终止这个线程。[AnyIO 的线程文档](https://anyio.readthedocs.io/en/stable/threads.html#running-a-function-in-a-worker-thread)明确区分了放弃等待与线程继续执行：忽略结果，仍然可能留下实际工作。

因此，并发名额应由真实工作持有到退出。如果外层协程一返回就释放名额，而线程仍在运行，下一个任务便可能立即进入，真实并发就超过了设定上限。可以让执行器持有受保护的工作任务，并在其真正结束后归还容量，同时回收完成状态和异常。

一个小回归至少应覆盖三件事：排队任务取消后没有开始工作；运行中任务取消后，名额一直保留到工作退出；其他未取消的任务最终仍能完成。只断言调用方收到了 `CancelledError`，覆盖不到后两层。

这些检查处理的是进程内的任务关系。HTTP 连接关闭、代理传播取消和远端计算停止还各有边界，需要分别确认，不能从本地一次取消异常推导整条链都已停工。
